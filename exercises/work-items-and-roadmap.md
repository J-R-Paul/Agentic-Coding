# A project is larger than one spec

The project is the broad undertaking. A roadmap lists its possible work items. A spec defines one chosen piece of work tightly enough that its completion can be checked independently.

## Examples in this course

| Level | Example | Appropriate record |
|---|---|---|
| Whole project | Study work, household circumstances and wellbeing using the teaching survey | Project brief and roadmap |
| One bounded work item | Produce the approved commute–life-satisfaction regression table, its reproducing script and short interpretation | `specs/05-commute-regression/spec.md` |
| A later work item | Address a newly identified sensitivity question with one additional comparison | A separate spec after the student chooses its scope |
| Routine implementation detail | Improve a figure caption without changing its data or interpretation | A bounded instruction and reviewed diff; a new research spec is unnecessary |
| Progress record | Record the current run command, checks and next authorized action | The work item's report and handover |

## The progression

Choose one deliverable. Make its substantive decisions. Draft its spec. Review and approve it. Request implementation separately. Check the evidence. Close that item or record an unresolved issue. Then choose the next item from the roadmap.

“Produce the entire project, all analyses and the final website” is not one scoped work item merely because it is written in one file. A title does not make a task bounded: it needs one coherent deliverable and a verifiable finish condition.

A supporting script, table and concise interpretation may belong together when they implement and explain the same approved analysis. They should not become an excuse to absorb unrelated analyses into the spec.

For the final challenge, begin with a new project brief. Decide how to divide the sponsor's larger commission. The spec skill should ask what single deliverable to specify first rather than converting the full sponsor brief into one oversized spec.
